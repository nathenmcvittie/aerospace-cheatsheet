# Contributing

A Raycast extension. `src/lib/` is pure logic and is where the tests live; `src/*.tsx`
are the command views; `tools/` generates every asset in the repo.

## Rule 0 — a change is not finished until the copy describes it

Shipping a feature and leaving the README describing the old product is the failure
mode this repo cares most about. **Every change that adds, removes, or alters something
a user can see means walking this list before opening a pull request.** Most changes touch two or
three of these; the point is to check all six, not to guess which.

| # | Surface | Where |
|---|---------|-------|
| 1 | Extension description | `package.json` → `description` |
| 2 | Command descriptions | `package.json` → `commands[].description` |
| 3 | README tagline, intro sentence, and the Commands table | `README.md` |
| 4 | The feature's own section in the README body | `README.md` |
| 5 | Changelog entry | `CHANGELOG.md` |
| 6 | GitHub repo description and topics | `gh repo edit` (not a file, easy to forget) |

Plus: **a screenshot**, if the change is visible. `metadata/` is generated by
`npm run screenshots`, which renders the extension's *own* row-building code against a
fixture, so a new view needs a new scene in `tools/gen-screenshots.mjs` rather than a
hand-taken capture.

Audit the current state of all six with:

```sh
python3 -c "import json;d=json.load(open('package.json'));print(d['description']);[print(' ',c['title'],'—',c['description']) for c in d['commands']]"
gh repo view --json description,repositoryTopics
grep -m2 -n "Look up" README.md
head -20 CHANGELOG.md
```

## Rule 1 — everything in assets/ and metadata/ is generated

Never hand-edit them. `npm run diagrams`, `npm run icon`, `npm run screenshots`.
CI regenerates and fails on any diff, so a stale committed asset breaks the build.

Two traps already hit here, both fixed, both worth not reintroducing:

- Diagrams contain **no key glyphs**. They are shared assets and the keystroke differs
  per user, so the key is rendered from live config beside the image. Baking `⌃⌥C` into
  a diagram makes it lie on anyone else's config.
- `src/lib/diagram-sizes.json` is generated in **Prettier's exact shape**. If the
  generator's output stops matching the formatter, `npm run diagrams` and `ray lint
  --fix` will rewrite the file against each other forever.

## Rule 2 — before every commit

```sh
npm run build && npm run test && npx ray lint
```

All three, every time. `ray lint` in particular is easy to skip and has caught a real
bug (a shortcut colliding with a Raycast reserved chord, which Raycast silently ignores
rather than reporting).

## Rule 3 — the config file is somebody's live window manager

`src/lib/editConfig.ts` writes to `~/.aerospace.toml`, which may be a symlink into a
dotfiles repo, and which controls whether the user's windows work.

- Edits are **line surgery on raw text**, never parse-and-reserialise. A round-trip
  through a TOML writer yields a valid file that has silently dropped every comment,
  blank line, and aligned column.
- Every write is transactional: re-parse, assert the intended outcome, write, then
  `reload-config --dry-run` as the final gate, and restore the original bytes on
  rejection. Only AeroSpace knows a command name it will not accept.
- Test edit logic against a fixture with comments, blank lines, aligned columns, and
  array values. Asserting "the file still parses" is not enough; assert that exactly
  one line changed and that its trailing comment survived.

## Rule 4 — check the CLI's real output, not its documentation

`aerospace list-windows --all --json` does **not** include the workspace unless
`--format` asks for it. That silently broke four commands, and nothing in the types or
the docs would have caught it. When adding a call, run it and read the actual keys.

Never run a state-changing `aerospace` command while testing unless the user has asked
for it: it rearranges their real windows. `list-*`, `config --get`, and `--help` are
safe. If a test must change state, wrap the restore in `finally`.
